# API reference

Every HTTP endpoint on the host `robroz-host`, as implemented on `main`. The route table is `host/src/lib.rs:router_from`. Request and response types are in `crates/robroz-contract/src/lib.rs`.

## Conventions

- **Address:** default `http://127.0.0.1:8790`, see `ROBROZ_ADDR` in [configuration.md](configuration.md). The examples below use `B=http://127.0.0.1:8790`.
- **Token:** when the host has `ROBROZ_TOKEN` or `ROBROZ_TOKEN_FILE` set, **every** `/api` request must send `Authorization: Bearer <your-token>`, including local ones. Missing or wrong returns 401 `{"error":"缺少或错误的令牌"}` (Missing or wrong token), with `WWW-Authenticate: Bearer` (`host/src/auth.rs:check_bearer`). With no token set, there is no auth. The examples below omit this header.
- **Format:** requests and responses are JSON, with camelCase field names. Send `Content-Type: application/json` with a JSON body.
- **Errors:** errors the host itself writes are `{"error":"原文"}` (`host/src/lib.rs:error_response`). A database error is always 500 `{"error":"数据库错误"}`.
- **Host text constants:** every Chinese string the host writes for the client (`error` bodies, card `progress` / `failure` / `reason`, delivery `summary`, settings test errors, Watchdog hints) is a `pub const` in `robroz_contract::host_text`. `HOST_UI_STRINGS` lists them all as `(name, text)`, including the older root constants such as `APPROVAL_EXPIRED_REASON`. A constant named `*_PREFIX` is followed by runtime text (an error, a name, a number). A constant named `*_SUFFIX` ends a sentence after a number; prefer `step_timeout_hint` / `stall_hint`, which build the whole line. Text built at run time (`step_timeout_hint`, `stall_hint`, `using_tool`, `router_step_progress`) is a function, not a `HOST_UI_STRINGS` entry. `router_step_progress(n, m)` is the Router step line 「{n}/{m} 步」 and `parse_router_step_progress` reads it back, and the client shows "Step n of m". `TOOL_CALL_FAILED_PREFIX` and `TOOL_STILL_NEEDS_APPROVAL` are tool results the host hands to the model; they are listed because a bro's reply can carry them onto a card. Clients should map these by constant, not by copied text. Text sent only to the model and log lines are not included.
- **Framework errors:** when the body is not valid JSON, a required field is missing, or an enum value is unknown, most endpoints are rejected by axum directly, with 400 / 415 / 422 and **plain text** (not `{"error"}`), for example 422 `Failed to deserialize the JSON body into the target type: missing field ...`. Endpoints marked “custom” below turn those cases into `{"error"}`.
- **ids:** ids generated by the server are UUID v4 strings. `botId` is supplied by the caller, any non-empty string.
- **Times:** RFC 3339, UTC, millisecond precision, ending in `Z`, for example `2026-11-21T02:35:48.932Z`.
- **Tenant:** single-tenant; `tenantId` is always `local`.
- **Users (v0.2):** the host has a `users` table. A request with the env token (`ROBROZ_TOKEN` / `ROBROZ_TOKEN_FILE`), or any request when no token is set, acts as the bootstrap admin (`id` `local-admin`, `name` `admin`, `role` `admin`; `robroz_contract::BOOTSTRAP_ADMIN_ID`). There is no user or per-user token API yet, so a single-user client sees no change. `GET /api/me` says who the caller is (`host/src/users.rs`).
- **Coded 403s (v0.2):** a 403 that is about *who* may act has a stable `code` next to `error`, so a client can tell it from a 401 (bad token). The client shows copy from `code` / `reason` and `ownerName` via its own i18n; the `error` field is for logs only. `not_bro_owner` (`robroz_contract::NotBroOwner`): the caller is not this bro's owner; the body also has `ownerUserId` / `ownerName` when known. `approval_forbidden` (`robroz_contract::ApprovalForbidden`): see [approve / deny](#post-apiapprovalsidapprove-and-deny).
- **Frozen fields:** existing fields are not changed; only optional fields are added. Clients must ignore unknown fields and skip unknown event `type`s; see [AGENTS.md](../AGENTS.md).

## Groups and members

A DM is a group with only one bro (`groups.dm_bot_id` is set in the database). Since v0.2 a DM also belongs to a user (`groups.dm_user_id`, the bro's owner), and there is at most one DM per (user, bro) (unique index `groups_dm_user_bot`). Every group endpoint works the same way on a DM.

### GET /api/me

The user the request acts as. `host/src/users.rs:me`

- 200 `Me` `{"id","name","role"}`; `role` is `admin` or `member`. Today this is always the bootstrap admin `{"id":"local-admin","name":"admin","role":"admin"}`.

### Bro owners

Every bro has an owner (`bots.owner_user_id`, `Bro.ownerUserId`). A bro made with `POST /api/bros`, or first added by `botId` with `POST /api/groups/{id}/members`, is owned by the caller. Bros from a v0.1 database are owned by the bootstrap admin. Only the owner may rename a bro, open its DM, add it to another group, or answer its approval cards; an admin is not an exception. Anyone else gets 403 `NotBroOwner` `{"error","code":"not_bro_owner","ownerUserId","ownerName"}`. `error` is `NOT_BRO_OWNER` (for logs only); the client shows "Only {owner} can change this bro." from `ownerName`. There is no `DELETE /api/bros/{id}` yet.

### POST /api/groups

Create a group. `host/src/lib.rs:create_group`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `name` | string | yes | Must be non-empty after trimming. |

- 201 `Group`: `{"id","name","tenantId"}`.
- 400 「请填写名称」: `name` is blank.
- 422 (plain text): `name` is missing.

```sh
curl -s -X POST $B/api/groups -H 'content-type: application/json' -d '{"name":"官网"}'
# {"id":"<groupId>","name":"官网","tenantId":"local"}
```

### GET /api/groups

List every group, **including DMs**, in creation order. `host/src/lib.rs:list_groups`

- 200 `{"groups":[Group]}`; with no groups, `{"groups":[]}`.

```sh
curl -s $B/api/groups
```

### POST /api/groups/{id}/members

Add a bro to a group. `host/src/lib.rs:add_member`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `botId` | string | yes | The bro's id. If it does not exist, a new bot is created. |
| `name` | string | yes | Used as the bot's name only when creating it. If the bot already exists this is **ignored**, and the name in the database is kept. |

- 201 `Member` `{"groupId","botId","name"}`: newly added. `name` is the name stored in the database.
- 200 `Member`: already in the group; not recorded twice.
- 400 「请填写名称」: `botId` or `name` is blank.
- 404 「群不存在」.
- 409 「私聊里只能有一个 bro」: adding another bro to a DM.
- 403 `NotBroOwner` (`code` `not_bro_owner`, plus `ownerUserId` / `ownerName`): `botId` is an existing bro owned by someone else. A new `botId` creates a bro owned by the caller.

Note: a bot's name is global. `@name` in a group matches that global name (see `/say`). Rename with `PATCH /api/bros/{id}`. A bot created here has no DM, and `dmGroupId` is `null`, until `POST /api/bros/{id}/dm`.

```sh
curl -s -X POST $B/api/groups/<groupId>/members -H 'content-type: application/json' \
  -d '{"botId":"bot-ada","name":"ada"}'
```

### POST /api/bros

Create a bro and its DM at the same time. `host/src/bros.rs:create_bro`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `name` | string | no | Trimmed, non-empty, at most 64 characters. If omitted, the default is `bro`, then the first free name from `bro 2` upwards (`robroz_contract::next_bro_name`). Names may be repeated. |

The body may be `{}`, or omitted entirely (and then `Content-Type` is omitted too). If `Content-Type: application/json` is sent with an empty body, axum returns 400 plain text.

- 201 `Bro` `{"id","name","dmGroupId","ownerUserId"}`. `id` is a UUID; `ownerUserId` is the caller.
- 400 「请填写名称」 / 「名字太长」 (Name too long).

```sh
curl -s -X POST $B/api/bros -H 'content-type: application/json' -d '{"name":"bob"}'
# {"id":"<botId>","name":"bob","dmGroupId":"<groupId>","ownerUserId":"local-admin"}
```

### GET /api/bros

List the caller's bots (including ones added only through `/members`), in creation order. `host/src/bros.rs:list_bros`

- 200 `{"bros":[Bro]}`. Without a DM, `dmGroupId` is `null`. `dmGroupId` is the caller's own DM with that bro. With one user (every v0.1 setup) this is every bot.

### PATCH /api/bros/{id}

Rename; the DM's group name is renamed with it. `host/src/bros.rs:rename_bro`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `name` | string | yes | Same rules as `POST /api/bros`. |

- 200 `Bro`.
- 400 「请填写名称」 / 「名字太长」.
- 404 「bro 不存在」.
- 403 `NotBroOwner` (`code` `not_bro_owner`, plus `ownerUserId` / `ownerName`): the caller is not the owner (admins included).

```sh
curl -s -X PATCH $B/api/bros/<botId> -H 'content-type: application/json' -d '{"name":"Bob"}'
```

### POST /api/bros/{id}/dm

Get the owner's DM with this bro, or create it. No body. `host/src/bros.rs:open_dm`

- 201 `Bro`: a DM was created.
- 200 `Bro`: it already existed.
- 404 「bro 不存在」.
- 403 `NotBroOwner` (`code` `not_bro_owner`, plus `ownerUserId` / `ownerName`): the caller is not the owner.

```sh
curl -s -X POST $B/api/bros/<botId>/dm
```

## Messages and /say

### POST /api/groups/{id}/say

Every line from the client's composer goes here. A `text` message is stored first, then the host decides whether to dispatch a task, in the same transaction. `host/src/say.rs:say`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `body` | string | yes | What is stored is the text after trimming. |

Whether a task is dispatched (`robroz_contract::route_mention`):

- In a DM: the whole line is dispatched to that bro; the prompt is the whole line.
- In a group: a task is dispatched only when the line starts with `@name` or `＠name`, the name is a (global) name of a group member, and the name is followed by whitespace or the end of the line. When more than one name matches, the longest wins (`@bro 2 …` goes to `bro 2`). The prompt is the text after `@name`, trimmed; if that is empty, no task is dispatched.
- Other cases do not dispatch a task directly, but a group still runs a turn (see below).

**Group turns** (`host/src/turns.rs`): every `/say` in a group (not a DM) gives each bro in the group one turn; a bro may stay silent.

- Order: the bro named with `@` goes first (that is the task above, unchanged: the prompt has `@name` stripped, the status card appears immediately, and it is returned in `Said.task`). The other members follow in join order. With no name, `Said.task` is still `null`, and every member takes a turn in join order.
- One at a time: the host only creates the next bro's task after every earlier turn has left `queued` / `running` (become `done` or `blocked`). That bro's prompt includes the original message and earlier bros' delivered results (at most 2,000 characters each), and tells it to reply with a single line `robroz-silent` if it has nothing to say (`robroz_host::turns::SILENT_REPLY`). Quoted text has every line starting with `robroz-` stripped, so someone else's line cannot trigger an outbound write, a progress update, or silence for this bro.
- Until the model replies, an unnamed turn is **hidden**: no status card, no unread, and it does not count in `lastActivityAt`. After the model replies:
  - If the reply is `robroz-silent` (that line alone; `robroz-progress:` lines do not count) or empty: the task becomes `done` and stays hidden. The client sees nothing: no message, no status card, no delivery, no unread.
  - If the model call fails, or no model is set up: treated as silence as well; no 「模型没回」 card is shown (only a log line).
  - Any other reply (including one that needs an MCP tool approval): the task appears from that moment, the status card's `createdAt` is that instant, and from then on it behaves like an ordinary task (sandbox, delivery, approval cards).
  - With the test switch `ROBROZ_MODEL=echo`, every turn speaks (it echoes the prompt).
- **Bros waking bros** (`robroz_host::turns::open_bro_round`). A person's `/say` opens a round at depth `PERSON_DEPTH` (0). When a bro's task on a group turn (the bro named with `@name`, or a bro that chose to speak on its turn) delivers a clean reply, the host opens a follow-on round at the parent round's depth + 1 for the other bros. A clean reply is one with no `failure` or `needsSetup` that is not silence.
  - The speaker never gets a turn in the round it opened. A bro whose turn in the parent round has not started yet is also left out, because that turn already quotes the reply.
  - A leading `@name` of another member in the reply moves that bro to the front. The rest follow in join order. The named bro still takes a normal turn (hidden until it speaks). This is never a follow-up, and no task card appears up front.
  - Turns work as above: one at a time, quoting earlier replies, hidden until the bro speaks, and waiting while the bro is busy. The prompt names the speaking bro and tells the bro to reply `robroz-silent` unless it is asked directly, needs to correct something, or has something essential to add.
  - Cap: `robroz_host::turns::MAX_BRO_DEPTH` (2). A reply in a depth-2 round is delivered but opens nothing, so one person message leads to at most two bro-opened levels.
  - Nothing else opens a round: not `POST /api/groups/{id}/messages`, not `POST /api/groups/{id}/tasks` or schedules (their tasks have no turn), not silence, not failed deliveries. DMs never have rounds.
  - No contract change. Bro-opened rounds post no `message` events; their replies show up as normal status and delivery cards.
- Turns for two messages run independently and do not wait for each other. If a bro is no longer in the group when its turn comes, it is skipped.
- If, when a bro's turn comes, it already has another task in this group that is `queued` / `running` (its own, or from another turn), this turn waits until that task leaves `queued` / `running` (`done` or `blocked`) before a new one is created, so the same bro does not run two tasks on the group's queue at once. Bros behind it stay behind it.

**Follow-ups** (`host/src/follow_ups.rs`): a line in a DM, or a line in a group that names a bro with `@name`, is attached to that bro's newest still-open task in this group (or DM) — `queued` / `running` / `blocked`, not counting hidden turn tasks — instead of starting a new task or a new status card.

- Only these count as a follow-up: that bro in a DM, or the bro named with a leading `@name` in a group, when that bro itself has an open task here. A group message with no name, or one that names a different bro, does not. A `done` task is not open, so a new task is created as usual.
- The follow-up text (after `@name` is stripped) is seen on this task's **next** step:
  - `queued`: `Follow-up:` and the text are appended to the prompt of the step about to run.
  - `running`: the current step finishes and delivers as usual. If it writes a result, the same task returns to `queued` for another step: the prompt includes the previous reply (with `robroz-` lines stripped) and the follow-up. So one status card can have two delivery cards.
  - `blocked`: the task still waits for the approval card; a follow-up is not `resume`. After the owner approves, the next step (or the step after an approved MCP call finishes) sees the follow-up; if the owner denies, the task ends as usual and the follow-up is unanswered.
  - If this step fails (「没写出结果」, over the outbound limit, and so on): the task ends as `done` + `failure` as usual, is not requeued, and the follow-up is unanswered.
- A follow-up in a group still opens a round: the named bro's turn is the task it was attached to, with no new hidden turn for that bro; the other bros wait until that task leaves `queued` / `running`, then take turns in join order, as after an ordinary name.
- No new card and no extra unread; the message itself is still a `message`.

Returns:

- 201 `Said` `{"message":Message,"task":Task|null,"appendedToTaskId"?:string}`. `task` is only the named task; tasks for the other turns are not returned here. On a follow-up, `task` is the task it was attached to (`state` is its current state, `prompt` is its original prompt), and `appendedToTaskId` is set (that task's id); the field is omitted when it is not a follow-up.

- 400 「请填写内容」: blank.
- 404 「群不存在」.

```sh
curl -s -X POST $B/api/groups/<groupId>/say -H 'content-type: application/json' \
  -d '{"body":"@ada 写一句欢迎语"}'
# {"message":{"id":"…","kind":"text","body":"@ada 写一句欢迎语","createdAt":"…"},
#  "task":{"id":"…","assigneeBotId":"bot-ada","prompt":"写一句欢迎语","state":"queued"}}
```

## Tasks and the pump

### POST /api/groups/{id}/tasks

Dispatch a task to a bro in the group, without going through `@`. `host/src/lib.rs:create_task`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `assigneeBotId` | string | yes | Must be a group member. |
| `prompt` | string | yes | Must be non-empty after trimming. |

- 201 `Task` `{"id","assigneeBotId","prompt","state":"queued"}`.
- 400 「请填写内容」 (checked first, including when the group does not exist).
- 404 「群不存在」.
- 400 「这个 Bot 不在群里」.

```sh
curl -s -X POST $B/api/groups/<groupId>/tasks -H 'content-type: application/json' \
  -d '{"assigneeBotId":"bot-ada","prompt":"写一句欢迎语"}'
```

### POST /api/tasks/{id}/resume

Resume a `blocked` task after a person has taken over. No body. `host/src/lib.rs:resume_task`

- 200 `{"id":"<taskId>","state":"queued"}`: appends the stored blocking-line hash to `ROBROZ_CONTROL/{taskId}/takeover`, clears the stuck record, and returns the task to `queued`. The pump later starts a new container on the same group folder and skips that line. If that line still has an unanswered task approval card, it is also marked `approved`.
- 404 「任务不存在」.
- 409 「这次不能恢复」 (This one can't be resumed): the task is not `blocked` (including `done`, and `done` with `failure` 「没写出结果」).
- 409 「请先回答审批卡」 (Answer the approval card first): the task is `blocked` on an MCP tool call. That block can only be approved or denied on the approval card, not with `resume`.
- 500 「恢复失败，找不到卡住记录」: there is no blocking-line record. The task stays `blocked`.
- 500 「恢复失败，无法写入接管标记」: writing the control folder failed. The task stays `blocked`.

```sh
curl -s -X POST $B/api/tasks/<taskId>/resume
```

### What the pump does

The pump is not an endpoint. It is a thread the host runs once a second (`host/src/main.rs:main` → `Host::tick_once`, `Host::pump_once` and `Host::watchdog_once`, implemented in `host/src/pump.rs` and `host/src/watchdog.rs`). Every task state change is written back by it; the client sees them as events. Model calls and the tool calls they start (including MCP and web search) run on a thread per task (`host/src/steps.rs`). The pump thread does not wait for them; it starts other containers and collects other results; when a reply is ready, the next pump pass starts that task's container.

1. `tick`: a routine that is due creates a new `queued` task (`briefing` is true). If the previous run is still queued or running, this firing is skipped and not made up later.
2. Take a `queued` task and set it to `running`. When a model is configured, call the model first (with memories, enabled skills, available tools, and MCP tools that are enabled for that group and whose server is `enabled`), and write the reply to `/control/reply.txt`. If the model wants to call an MCP tool that needs approval, the task becomes `blocked`, an approval card with `action` `call` is issued, and this step does not write `reply.txt` or start a container; after approval it continues from where it paused.
3. `docker run`, with the container `--network none`, mounting only the group folder at `/workspace` and `/control` read-only. If it cannot start, the task returns to `queued`.
4. After the container exits:
   - It wrote `result.txt`: `done`, and a delivery card is issued.
   - The prompt has a `robroz-action:external` line that has not been taken over: `blocked`, and the host issues a task approval card (`waitingFor:"approval"`).
   - It hits `robroz-action:captcha`: `blocked`, waiting for a takeover (`waitingFor:"takeover"`).
   - Over the outbound limit, or a method other than GET: `done` with `failure`, no delivery.
   - Non-zero exit, no result written, or the container disappeared: `done`, `failure` 「没写出结果」 (Finished with no result), no delivery, no requeue, and no new container. The database write is compare-and-set (it only takes effect while the task is still `running`).
5. For a successfully finished task, read its `proposals.jsonl` and issue a confirm card for each memory or skill proposal.
6. Watchdog (`host/src/watchdog.rs`):
   - A task that is `running` with `containerUp` false (a failed run left by an older host) is also ended as `done` + `failure` 「没写出结果」, with no requeue.
   - A step that has run for half of `ROBROZ_STEP_TIMEOUT_SECS` (300 seconds at the default 600): a log line, and `progress` becomes 「模型和工具还没回，已等 N 分钟」 (`step_timeout_hint`, N is the minutes waited so far; the client shows No reply from the model or tools for N min). This is only a hint; the step keeps running until the full timeout, when step 7 cancels it.
   - A live container whose `progress` has not changed for `ROBROZ_STALL_SECS` (default 900 seconds): a log line, and `progress` becomes 「N 分钟没有新进度」 (No new progress for N min). When the runner writes new progress, that new line replaces it. Hint only: the state does not change, the container is not stopped, and the task is not requeued. `blocked` is waiting for a person and does not count as a stall.
7. Step timeout (`host/src/timeouts.rs`). A step is the model phase after a claim (the model call and its tool calls), each Router step, or the container run. Each starts its own clock, stored in SQLite (`step_clocks`), so a host restart does not reset it. When a `running` task's step reaches `ROBROZ_STEP_TIMEOUT_SECS` (default 600 seconds), the next pump pass cancels it. The Watchdog hint in step 6 comes at half that time, so the card shows it first:
   - The container is stopped with `docker rm -f`. If that fails, the task stays `running` and the next pass tries again.
   - A step still on its thread is told to stop before its next model or tool call. Whatever it returns later is dropped.
   - The task ends as `done` + `failure` 「没写出结果」 (`robroz_card::NO_RESULT`), the same as a failed Router step: no delivery, no requeue, and the Router plan is dropped. A hidden group turn ends silent instead (no card).
   - Time spent `blocked` on an approval card or a takeover is not step time. The claim after the card is answered starts a fresh clock.
   - No new client-visible text: the card shows the existing 「没写出结果」 (Finished with no result).

The full permission rules are in [permissions.md](permissions.md). Container and model-call details are in [architecture.md](architecture.md).

## Events and cards

### GET /api/groups/{id}/events

Every card in the group. `host/src/lib.rs:list_events`, assembled in `host/src/lib.rs:group_events`.

| Query | Required | Notes |
| --- | --- | --- |
| `since` | no | RFC 3339. Only cards that **changed after** this time are returned. An empty value is the same as omitting it. |


### Task state and labels

`state` is frozen to four values. `label` comes from `robroz_card::status_line(state, containerUp)` and is still Chinese on the wire:

| `state` | `containerUp` | `label` |
| --- | --- | --- |
| `queued` | false | 「排队」 (Queued) |
| `running` | true | 「进行」 (Running) |
| `running` | false | 「没写出结果」 (Finished with no result). Only in old data: the host now ends a failed run as `done` + `failure` 「没写出结果」, and the Watchdog ends any remaining such tasks the same way. |
| `blocked` | false | 「卡住」 (Stuck) |
| `done` | false | 「完成」 (Done). When `failure` is set the client shows Couldn't finish: {reason} (「没做成：原因」); when `failure` is 「没写出结果」 it shows Finished with no result as it is. |

### failure

A status card may carry this only when `done`; when there is also a delivery card, that card has the same value. It is cleared when the task runs again. The stored value is the original Chinese:

| Case | `failure` | Delivery card? | Code |
| --- | --- | --- | --- |
| The model call failed | 「模型没回：<原因>」 (No reply from the model: {reason}) | Yes; the delivery has the same `failure` | `host/src/pump.rs:write_reply`, `host/src/tools.rs` |
| A task approval card was denied | 「你拒绝了：<first ordinary line of the prompt, at most 60 characters>」 (You denied: …) | No | `host/src/approvals.rs:settle_task` |
| An MCP tool approval card was denied | 「你拒绝了：{server}.{tool}」 (You denied: {server}.{tool}) | Yes; `summary` is 「未执行」 (Didn't run); the delivery has the same `failure` | `host/src/mcp_tools.rs:finish_denied` |
| A task or MCP tool approval card expired | 「审批已过期」 (`APPROVAL_EXPIRED_REASON`, Approval expired) | No for a task card; yes for an MCP card, with `summary` 「未执行」 | `host/src/review/mod.rs:expire_due` |
| Over the outbound limit | 「出网超额：已用 N 次，上限 M」 (assembled in `robroz-policy`; not mapped yet) | No | `crates/robroz-policy/src/lib.rs` (`OverQuota::failure`) |
| Outbound used a method other than GET | 「出网只允许 GET：用了 <method>」 (not mapped yet) | No | same |
| More than 8 rounds of tool calls | 「工具调用超过 8 轮」 (Stopped after 8 rounds of tool calls) | Yes; the delivery has the same `failure`, and the result file has the same sentence | `host/src/tools.rs:ROUND_LIMIT_FAILURE` |
| A dead run (non-zero exit, no result, or the container disappeared) | 「没写出结果」 (Finished with no result) | No | `host/src/pump.rs` (`Outcome::Dead`), `host/src/watchdog.rs` (`DEAD_RUN_FAILURE`) |

### waitingFor

Present only while `blocked`:

- `approval`: this task has an **unanswered** approval card for its current blocking line (`robroz-action:external`, or an MCP write-tool `call` card). Answering that card is enough: approve returns it to the queue and it continues; deny ends it as `done` with `failure`.
- `takeover`: there is no such approval card (for example `robroz-action:captcha`); a person takes over and then calls `POST /api/tasks/{id}/resume`. An MCP write tool cannot be released with `resume`.

### progress

Present only while `running` with `containerUp` true, or while the task is `blocked` on an MCP approval and a progress line is still stored. It is updated in place on the status card (`host/src/progress.rs`):

- Since v0.2 the host no longer writes `APPROVAL_SENT_TO_OWNER_DM_NOTICE` (「已发到主人私聊」): approval cards stay in the task's group (see [Where approval cards go](#where-approval-cards-go)). The constant stays in the contract for old clients.
- The host reports key moments itself: 「开始干活」 (Getting started) when the run begins, or 「在想怎么回」 (Thinking about a reply) when a model is attached; 「在沙箱里跑」 (Running in the sandbox) after the sandbox is up; 「在用 <工具名>」 (Using {name}) when a tool is called. MCP tools use the display name `{server}.{tool}`. The line stays while waiting for approval.
- The bro can report too: a line `robroz-progress:<text>` in the prompt or in the model reply; the last such line is used.
- When a bro's internal Router splits a task into 2–3 steps (`running` with the container up), this line is exactly `router_step_progress(n, m)`, that is 「{n}/{m} 步」, and is not combined with other text, including 「在想怎么回」 or 「在用 <工具名>」. A `robroz-progress:` line from the bro does not cover it. Clients can read n and m with `parse_router_step_progress`; the client shows "Step n of m". While `blocked` on an MCP approval the usual approval progress shows instead, not 「n/m 步」. A task that is not split (the plan failed, there is only one step, there is no model, or `ROBROZ_MODEL=echo`) never shows n/m. A Watchdog hint may still temporarily replace this line.
- The Watchdog may also write 「模型和工具还没回，已等 N 分钟」 (No reply from the model or tools for N min, at half of `ROBROZ_STEP_TIMEOUT_SECS`) or 「N 分钟没有新进度」 (No new progress for N min). These are hints only and do not change the state. A step that reaches `ROBROZ_STEP_TIMEOUT_SECS` is cancelled and the task ends as `done` + 「没写出结果」; see step 7 of [What the pump does](#what-the-pump-does).
- The text is normalized to one line: consecutive whitespace becomes a single space, ends are trimmed, at most 60 characters (longer text is cut to 59 characters plus 「…」). `updatedAt` is not updated when the text has not changed.

### needsSetup

An optional field on a delivery card. There are two values today, independent of `failure`:

- `"search"`: the task called `web_search` but web search is not set up (`web_fetch` does not record this). The task usually still writes a result, with `needsSetup` and no `failure`.
- `"model"`: no model is set up (and the test switch `ROBROZ_MODEL=echo` is off). The result file is 「还没设置模型」 (No model set up yet); the prompt is not written through as the result.

The client should send the user to the matching settings from this field, and must not match on the text. For search, see [client.md, Web search page](client.md#web-search-page); for the model, [client.md, Model page](client.md#model-page).

### GET /api/groups/{id}/stream

Server-Sent Events, `text/event-stream`. `host/src/stream.rs:stream_events`

| Input | Notes |
| --- | --- |
| Header `Last-Event-ID` | Used on reconnect; only changes after this time are replayed. Wins over `since` when both are present. |
| Query `since` | Same meaning. |

- Each event: `event:` is the event `type`, `id:` is the time this card changed, `data:` is the event JSON (the same as in `/events`).


## Unread

One read position per group, for a single user. `host/src/unread.rs`

`Unread`: `{"groupId","readAt","unread","lastActivityAt"}`. `readAt` is `null` if the group has never been read; `lastActivityAt` is `null` if the group has had no activity.

`unread` only counts things a bro sent after `readAt` that a person needs to see: delivery, choice, approval, `approval_reminder` and confirm cards (by `createdAt`), and tasks whose `updatedAt` is after that time and that are currently `blocked`. Hidden group-turn tasks (see group turns under `/say`) are not counted, and they do not count in `lastActivityAt`. A person's own messages, and status changes such as queued, running or done, are not counted. Approval cards only count once they have been issued (cards still in review, or auto-approved, do not), and in the conversation where the card sits. A group card also counts once in the owner's DM, as its `approval_reminder`.

`lastActivityAt` is the newest time among messages, tasks (`updatedAt`), deliveries, choices, approvals and confirm cards (answered ones use `answeredAt`). A reminder counts as activity in the DM.

### GET /api/unread

- 200 `{"groups":[Unread]}`, including DMs. Newest `lastActivityAt` first; groups with no activity come last, in creation order.

### GET /api/groups/{id}/unread

- 200 `Unread`; 404 「群不存在」.

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `readAt` | string (RFC 3339) | no | Defaults to now. The read position only moves forward; an earlier value is ignored. |

The body may be omitted (and then `Content-Type` is omitted too).

- 200 the updated `Unread`.
- 400 「readAt 不是合法时间」.
- 404 「群不存在」.

```sh
curl -s -X POST $B/api/groups/<groupId>/read -H 'content-type: application/json' -d '{}'
```

### POST /api/groups/{id}/approvals

A bro asks a person before deleting, sending or spending. `host/src/approvals.rs:create_approval`

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `botId` | string | yes | Must be a group member. |
| `action` | `"delete"` \| `"send"` \| `"spend"` | yes | An unknown value returns 400 「不支持这个动作」. `call`, `rule_add` and `rule_delete` can only be issued by the host; sending them on this endpoint returns 400 「这个动作只能由宿主机发出」. |
| `summary` | string | yes | Non-empty after trim, one line, at most 200 characters. |
| `path` | string | no | Display only; a whitespace-only value is treated as omitted. |

The host runs auto-review first (see [Auto-review and expiry](#auto-review-and-expiry)). Review finishes inside this request, so with Allow rules you may wait a few seconds for the review model. A 201 body is always the card after review, in the same shape as before (no `taskId`):

- No Allow rules: `decision: null`, with `expiresAt`, no `reason`. The card stays in this group (see [Where approval cards go](#where-approval-cards-go)).
- A rule allows it: `decision: "approved"`, `answeredAt` is set, `answeredBy` is `null`, `reason` is the review model's reason, and there is no `expiresAt`. - Blocked (including a review error after retry, or no model): `decision: null`, with `reason` and `expiresAt`; the card stays in this group.
- The bro should look at `decision`: `approved` means go ahead, `null` means wait for the owner (`GET /api/approvals/{id}` or the stream), `denied` means do not. An older bro that treats 201 as “a card was issued” will not error, but on an allowed card it will wait for a card that never appears — so the bro should check `decision` first.

- 404 「群不存在」; 400 「这个 Bot 不在群里」.

### Where approval cards go

Since v0.2 an approval card stays in **the conversation where it was raised** (`host/src/approvals.rs:card_group`, `bro_card_group`). This covers task approval cards, MCP tool approval cards and cards a bro posts with `POST /api/groups/{id}/approvals`.

- **Group (not a DM):** the card, with its buttons, is only in the group. Only the bro's owner (`ownerUserId`) may answer it. The owner's DM with that bro gets an `approval_reminder` (see [Event types](#event-types)): no buttons, it links to the group, and its `state` follows the card. If the owner has no DM with the bro yet, the host creates one, the same as `POST /api/bros/{id}/dm`. The status card is `blocked` + `waitingFor:"approval"` and no longer shows 「已发到主人私聊」.
- **DM:** the card and its buttons stay in the DM. There is no reminder.
- Both SSE streams follow the card: the group stream pushes the `approval`, and the DM stream pushes the `approval_reminder`, once when it is raised and again when it is answered or expires.
- After approval the task is requeued in its group, finishes in the group folder, and the delivery is in the group.
- Older data: a card that v0.1 moved into a DM is still listed in both places as before.

### Task approval cards

When the task's prompt has a `robroz-action:external` line that has not been taken over, the host issues an approval card for the assignee (`host/src/approvals.rs:gate_task`): `action` is `send`, `summary` is 「要对外写入：<first ordinary line of the prompt, at most 60 characters>」 (Writes to an outside service: …), with `taskId`, in the task's group (see above), and the status card has `waitingFor` `approval`.

- Approve: write the takeover marker, requeue the task, and run to the end skipping that line.
- Deny: the task becomes `done`, `failure` 「你拒绝了：…」 (You denied: …), no delivery card.
- If the task was already taken over with `/resume`, answering only records the decision and does not move the task.
- Auto-review and expiry are under [Auto-review and expiry](#auto-review-and-expiry).

### MCP tool approval cards

When the model wants to call an MCP tool that is not marked `readOnlyHint: true`, the host issues an approval card for the assignee (`host/src/approvals.rs:gate_mcp_task`): `action` is `call`, `summary` is 「调用 {server}.{tool}」 (the client shows Call {server}.{tool}) plus a parameter summary (truncated past `APPROVAL_SUMMARY_MAX`), with `taskId`, `mcpServer` and `mcpTool`, in the task's group (see above). The status card has `waitingFor` `approval`, and the progress line is 「在用 {server}.{tool}」 (Using {server}.{tool}).

- Approve: the task returns to `queued`; the pump makes the call, returns the result to the model, and continues. The call counts as one outbound GET. If writing the continue marker fails, 500 「批准失败，无法写入继续标记」, and the card stays unanswered.
- Deny: the call is not made; the task becomes `done`, the delivery `summary` is 「未执行」 (Didn't run), and `failure` is 「你拒绝了：{server}.{tool}」 (You denied: {server}.{tool}).
- Do not use `POST /api/tasks/{id}/resume` instead of answering the card (409 「请先回答审批卡」, Answer the approval card first).
- Auto-review and expiry are the same as for a task approval card; see [Auto-review and expiry](#auto-review-and-expiry).
- A read-only MCP tool does not raise a card. Behaviour is in [search-and-mcp.md](search-and-mcp.md#模型怎么调用).

### Auto-review and expiry

`host/src/review/`. Design: [design/auto-review.md](design/auto-review.md).

- **No Allow rules:** task and MCP tool approval cards are issued as before, with no review model, no `reason`, and with `expiresAt`.
- **With Allow rules:** the card is not issued yet (it is not in events; `approve` / `deny` return 404). The host's review thread sends every confirmed rule's text and this action to the review model, which replies allow or block plus one sentence of reason. No regex or wildcards.
  - allow: no card is shown; the same markers are written as a manual approval, and the task is requeued. The database records `decision` `approved` and the reason, with no `answeredBy`.
  - block: the card is issued, with `reason` and `expiresAt`; `createdAt` is updated to the issue time.
  - A review error or timeout: retry once, then block, with `reason` 「自动审核没有成功，需要你批准」 (Auto-review failed. Needs your approval.).
  - No model: block, with `reason` 「还没设置模型，没法自动审核」. It never defaults to allow.
- **Expiry:** if the card is still unanswered at `expiresAt` (`ROBROZ_APPROVAL_TTL_SECS` after it was issued, default 24 hours), the host records `decision: denied`, `reason: "审批已过期"` (`APPROVAL_EXPIRED_REASON`, Approval expired), and leaves `answeredBy` empty. A task it was gating becomes `done`, `failure` 「审批已过期」. A later `approve` / `deny` returns 403 `approval_forbidden` with `reason` `expired`. A card past `expiresAt` that the sweep has not reached yet is expired on the spot and gets the same 403. Confirm cards (memory, skill) and a takeover (captcha) do not expire.

Task approval cards, MCP tool approval cards and bro-issued cards all go through the review above; a blocked card stays where it was raised, see [Where approval cards go](#where-approval-cards-go). A bro-issued card is not reviewed on the review thread; it is reviewed in the `POST /api/groups/{id}/approvals` request itself (the model is called outside the lock). If the request drops mid-review, the review thread takes over after 60 seconds. A card allowed by a rule (including a task card) can be read with `GET /api/approvals/{id}`; `approve` / `deny` return 403 `approval_forbidden` with `reason` `decided`. A card still in review is 404 at both. Unread only counts issued approval cards (and their reminders), not cards in review or auto-approved ones, see [Unread](#unread).

### GET /api/approvals/{id}

Read one approval card; the body is the same `approval` object as in events. `host/src/approvals.rs:get_approval`. Allow-rule confirm cards on the settings page can only be fetched from here.

- 200 an `approval` object.
- 404 「审批卡不存在」: the id does not exist, it is a confirm card (`confirm`), or the card is still in auto-review. A card auto-approved (never issued) can still be read, with `decision` `approved` and a `reason`.

```sh
curl -s $B/api/approvals/<approvalId>
```

### POST /api/approvals/{id}/approve and /deny

Answer an approval card, and also a confirm card (see [Confirm cards](#confirm-cards)). `host/src/approvals.rs:approve`, `deny`; shared logic in `decide`.

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `answeredBy` | string | no | The whole body may be omitted, or `{}`. |

- 200 the same card, with `decision` `approved` / `denied`, and `answeredAt` and `answeredBy` filled.
- 404 「审批卡不存在」: the id does not exist (the same for a confirm card), or the card is still in auto-review.
- 403 `ApprovalForbidden` (v0.2; was 409 before): the caller may not answer this card. The body is `{"error","code":"approval_forbidden","reason","ownerUserId"?,"ownerName"?}` (`robroz_contract::ApprovalForbidden`). The client shows copy from `code` / `reason` and `ownerName`; `error` is for logs only. `reason` is exactly one of:
  - `not_owner`: the caller is not the bro's owner (client: "Only {owner} can approve this."). For an Allow-rule card: the caller is not an admin. Checked first, so a non-owner gets `not_owner` even on a decided card.
  - `decided`: the card was already answered, by a person or by auto-review. The client does not show an error; it reloads the card and shows the result.
  - `expired`: the card expired. The client does not show an error; it shows that the card has expired.
  `ownerUserId` / `ownerName` name the bro's owner, so the client can say who to ask; they are omitted for Allow-rule cards. `code` is stable and a 403 is never a token problem (that is 401).
- 409 「已经答过了」: a memory or skill confirm card that was already answered (unchanged).
- Approving a `rule_add` card adds that rule; approving a `rule_delete` card deletes it. Deny or expiry leaves the rule list unchanged.
- 400 「answeredBy 只能一行，最多 40 个字」.
- 422 「请求格式不正确」 (custom): the body is not valid JSON.
- 500 「批准失败，无法写入接管标记」: writing the control folder failed when approving a task card; the card stays unanswered.
- 500 「批准失败，无法写入继续标记」: writing the continue marker failed when approving an MCP tool card; the card stays unanswered.

```sh
curl -s -X POST $B/api/approvals/<approvalId>/approve
# not the owner:
# 403 {"error":"只有这个 bro 的主人能这样做","code":"approval_forbidden","reason":"not_owner","ownerUserId":"u-mei","ownerName":"Mei"}
curl -s -X POST $B/api/approvals/<approvalId>/deny -H 'content-type: application/json' -d '{"answeredBy":"书房电脑"}'
```

### answeredBy

Shared by choice, approval and confirm cards. The host has a single shared token and cannot tell who is acting, so it stores the device or person name the client reports, without checking it. Leading and trailing whitespace is stripped; an empty value is treated as omitted; one line only, at most 40 characters (`robroz_contract::clean_answered_by`). When omitted, the event field is `null`.

## Confirm cards

A bro cannot write a memory or skill directly; it can only propose, and a person decides on a confirm card. Code: `host/src/proposals.rs`.

- **How to propose:** a line in the prompt or the model reply, `robroz-memory:{"kind":"habit","text":"周报用中文","scope":"user"}`, or `robroz-skill:{"slug":"weekly-report","title":"写周报","instruction":"先列三点","scope":"user"}`. `scope` may be omitted; it defaults to `bot:<assignee>`. The runner writes them to the group folder as `tasks/{taskId}/proposals.jsonl`; these lines do not go into `result.txt`.
- **When they are collected:** when the task is `done` with no `failure`, the host reads this file and then deletes it. Each item is stored as a memory or skill with `source=bot`, `status=pending`, and a `confirm` card is issued.
- **What is not collected:** bad JSON, an unknown `type`, illegal fields, a bad `scope` or a missing bro; a memory with the same `scope`, `kind` and text (consecutive whitespace counts as one) that already exists and has not been forgotten (any status); a skill with the same `slug` that already exists and has not been forgotten. At most 20 items are collected per task (`PROPOSALS_PER_TASK_MAX`).
- **Answering:** `POST /api/approvals/{confirmId}/approve` (becomes `kept`) or `/deny` (becomes `rejected`). The body, `answeredBy` and 404 「审批卡不存在」 are the same as for an approval card, and only the bro's owner may answer (403 `approval_forbidden`, `reason` `not_owner`). An already answered confirm card still returns 409 「已经答过了」. This is the only way to change `status`.
- Confirm cards live in the same table as approval cards, but they only appear as a `confirm` event and do not affect a status card's `waitingFor`. A new card counts as one unread.
- If a `pending` memory or skill is changed with `PATCH`, the confirm card is pushed again with the new content.

```sh
curl -s -X POST $B/api/approvals/<confirmId>/approve -H 'content-type: application/json' -d '{"answeredBy":"书房电脑"}'
```

## MCP server settings

The host acts as an MCP client, and supports stdio (a local process) and Streamable HTTP. Configuration is in `host/src/mcp.rs`, connections in `crates/robroz-mcp`, with a 10-second connect timeout. When a task starts, tools from servers that are enabled in that group and whose server is `enabled` are registered into the model loop (`host/src/mcp_tools.rs`); see [MCP tool calls](#mcp-tool-calls).

A stdio server starts `command` on the host, as the host user. Only fill in commands you trust. Until it is approved, `/test`, `/tools` and registration in the model loop will not start the process; call `POST /api/mcp/servers/{id}/approve-command` first to approve the current `command` and `args`. HTTP servers do not need this approval.

`McpServer`:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | |
| `name` | string | Unique, one line, at most 80 characters. |
| `transport` | `"stdio"` \| `"http"` | |
| `command` | string | Optional, stdio only. |
| `args` | string[] | Optional, stdio only. |
| `url` | string | Optional, HTTP only. |
| `secrets` | `[{"name","in","hasKey","keyLast4"?}]` | `in` is `env` (an environment variable for stdio) or `header` (an HTTP request header). Secret values are never returned. |
| `enabled` | bool | |
| `toolCount` | number | Optional; the number of tools seen on the last successful connection. |
| `createdAt` / `updatedAt` | string | |
| `commandApproved` | bool | Optional, stdio only. Whether the current `command` and `args` have been approved. New servers, and existing ones after a migration, are `false`. HTTP servers do not return this field. |
| `commandApprovedAt` | string | Optional; present when approved, the approval time. |

Secret input `McpSecretInput`: `{"name","in"?,"key"?}`. `name` is non-empty, has no whitespace, and is at most 64 characters. If `in` is omitted, stdio defaults to `env` and HTTP to `header`. Omitting `key` leaves the value unchanged (only meaningful on `PATCH`); `null` deletes that secret; a string sets it.

A malformed body is always 400 「请求格式不正确」 (custom).

### GET /api/mcp/servers

- 200 `{"servers":[McpServer]}`, newest `updatedAt` first.

### POST /api/mcp/servers

| Request field | Type | Required | Notes |
| --- | --- | --- | --- |
| `name` | string | yes | |
| `transport` | string | yes | `stdio` or `http`. |
| `command` | string | required for stdio | |
| `args` | string[] | no | |
| `url` | string | required for HTTP | Must start with `http://` or `https://`. |
| `secrets` | McpSecretInput[] | no | A new secret must include `key`. |
| `enabled` | bool | no | Default true. |

- 201 `McpServer`.
- 409 「这个名字已经有了」.
- 400 「请填写名称」 / 「名称最多 80 个字」 / 「名称只能一行」 / 「transport 只能是 stdio 或 http」 / 「请填写启动命令」 / 「启动命令无效」 / 「参数无效」 / 「请填写地址」 / 「地址要以 http:// 或 https:// 开头」.
- 400 「请填写密钥名称」 / 「密钥名称最多 64 个字」 / 「密钥名称里不能有空白」 / 「新增密钥时请填写值」 / 「密钥不能为空」.

```sh
curl -s -X POST $B/api/mcp/servers -H 'content-type: application/json' \
  -d '{"name":"docs","transport":"http","url":"https://<MCP 服务器地址>/mcp","secrets":[{"name":"Authorization","key":"Bearer <你的令牌>"}]}'
```

### PATCH /api/mcp/servers/{id}

The fields are the same as `POST`, all optional; only the fields that are sent are changed. Changing `transport` clears the fields of the other transport; `command` and `url` may be `null`. After the change, stdio must have `command` and HTTP must have `url`. If the resulting `command` or `args` no longer match what was recorded at approval (including a change of transport), `commandApproved` is automatically set back to `false` and must be approved again.

- 200 `McpServer`.
- 404 「MCP 服务器不存在」; 409 「这个名字已经有了」; 400 same as `POST`.

### DELETE /api/mcp/servers/{id}

- 204, and it is also disabled in every group.
- 404 「MCP 服务器不存在」.

### GET /api/mcp/servers/{id}/tools

Connects once live, lists tools, and on success updates `toolCount`. A stdio server must have its start command approved first, or the process is not started.

- 200 `{"tools":[{"name","description"?,"needsApproval"}]}`. `needsApproval` is false only when the tool is marked `readOnlyHint: true`; otherwise true.
- 404 「MCP 服务器不存在」.
- 409 `{"error":"command_not_approved","command","args"}`: the stdio command has not been approved. `command` and `args` are the current configuration.
- 502 `{"error":"<原因>"}`: cannot connect, for example 「连不上 MCP 服务器：…」. Keys in the reason are replaced with `***`.

### POST /api/mcp/servers/{id}/test

- 200 `{"ok":true,"toolCount":N}` or `{"ok":false,"error":"<原因>"}`.
- 404 「MCP 服务器不存在」.
- 409 `{"error":"command_not_approved","command","args"}`: same as `GET …/tools`; the process is not started until approved.

### POST /api/mcp/servers/{id}/approve-command

Marks this stdio server's current `command` and `args` as approved, and records the fingerprint and `commandApprovedAt` from that approval. No body. Approving again is still 200 and updates the approval time.

- 200 `McpServer`, with `commandApproved` true.
- 404 「MCP 服务器不存在」.
- 400 「只有 stdio 服务器需要批准启动命令」 / 「请填写启动命令」.

```sh
curl -s -X POST $B/api/mcp/servers/<serverId>/approve-command
```

### GET /api/groups/{id}/mcp

- 200 `{"servers":[McpServer]}`: servers enabled in this group (including ones whose `enabled` is false).
- 404 「群不存在」.

### GET /api/groups/{id}/mcp/{serverId}

- 200 `McpServer`.
- 404 「群不存在」 / 「MCP 服务器不存在」 / 「这个群还没启用这台服务器」.

### PUT /api/groups/{id}/mcp/{serverId} and DELETE

Enable / disable in the group. No body.

- 204; calling again is also 204.
- 404 「群不存在」 / 「MCP 服务器不存在」.

```sh
curl -s -X PUT $B/api/groups/<groupId>/mcp/<serverId>
```

### MCP tool calls

When a task starts, the host registers MCP tools from servers enabled in that group whose server is also `enabled` into this model loop (`host/src/mcp_tools.rs:register_tools`). If a server fails to connect it is skipped and the task continues. A stdio server whose start command is not yet approved is also skipped, and the process is not started. A server that is not enabled in the group, or whose server is turned off, is not registered.

- The name given to the model is `{safe_server}__{safe_tool}` (only letters, digits, `_` and `-`, at most 64 characters; a short hash is added on a clash). Progress lines and approval cards still use `{server}.{tool}`.
- `readOnlyHint: true`: counted as one outbound GET, called directly, no approval card.
- Anything else: the MCP tool approval card above is issued first; after approval the call is made (also one outbound GET) and the result is returned to the model; on deny it is not executed.
- If the call fails, the model receives 「调用失败：{原因}」 (Call failed: {reason}), and the task does not fail because of it.
- Tool results, like other host tools, are cut at 16,000 characters, with `\n…(truncated)` appended (`TRUNCATED_MARK` in `host/src/tools.rs`).
- The contract only added optional fields and a new type: `ApprovalAction::Call` (JSON `"call"`), and optional `mcpServer`, `mcpTool` on `Event::Approval`. Existing fields and task states are unchanged.

Behaviour is in [search-and-mcp.md](search-and-mcp.md#模型怎么调用) and [permissions.md](permissions.md#mcp-tools).
